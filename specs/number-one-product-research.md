# Number One Product Research

Updated: 2026-05-27

## Mission

Jini should become number 1 in its category by being the most dependable,
frugal, and outcome-focused work operating system across CLI, desktop, and
mobile.

That is not the same as being "another coding agent" or "another shell." The
winning category is:

- one stable work object
- one continuation model
- one quality-upstream system
- one cross-surface session loop
- one self-learning and self-correcting framework

The product should improve user output faster than competitors while requiring
fewer repeated setup actions and fewer user-facing release changes.

## Competing Framework Evolution

### OpenAI Codex

Codex is evolving toward long-running delegated work, multi-agent tasking,
cross-device approvals, remote environment access, hooks, and enterprise-safe
automation. The key shift is not just better coding. The key shift is that
work can keep moving while the user is away from the primary machine.

Implication for Jini:

- continuation must be cross-surface by default
- approvals must be interruptible and resumable
- long-running work must remain inspectable and steerable
- mobile is not a companion app; it is a continuity surface

### Claude Code

Claude Code is evolving toward specialized subagents, deep hook coverage,
memory layers, and scoped control over tools and prompts. The product shape is
becoming a configurable operating layer, not just a chat wrapper.

Implication for Jini:

- specialization should be policy-driven, not prompt-copy driven
- memory should change behavior at the right step, not just persist notes
- hooks should move quality and governance upstream automatically
- user, repo, and org context should be layered into one session graph

### GitHub Copilot And GitHub CLI

GitHub is evolving Copilot toward custom agents, skills, MCP connectivity,
cloud-agent task orchestration, and tight GitHub-native workflow integration.
GitHub CLI remains a strong extension host and command backbone.

Implication for Jini:

- Jini must be GitHub-native where engineering work is concerned
- issue, PR, review, and wiki flows should feel first-class, not bolted on
- reusable skills and agents should be generated from canonical Jini state
- extension behavior should be auditable, replayable, and scoped

### Kiro

Kiro is evolving toward durable steering, team-wide conventions, and lifecycle
hooks that can be rolled out at the org level.

Implication for Jini:

- Jini should learn conventions from the repo and team automatically
- steering should be partly generated from observed behavior, not only written
- the system should reduce manual policy file authoring over time

### Gemini CLI

Gemini CLI is evolving fast through preview, stable, and nightly release
channels, built-in grounding, checkpointing, GitHub workflows, and MCP-based
expansion.

Implication for Jini:

- competitors can ship surface features faster than Jini can
- Jini cannot rely on matching weekly feature releases
- Jini must win through policy updates, learning, and self-correction layers
- the product must improve from traces, evaluations, and environment learning
  more than from constant UX churn

### Aider, Cline, And Goose

These tools are converging on three strong ideas:

- compact repository understanding
- explicit planning versus execution modes
- extension-based capability growth

Implication for Jini:

- repo understanding should be cheap, compact, and always available
- planning, doing, reviewing, and resuming should be explicit states of one
  work object
- extension growth should not fragment the user experience

## What The Market Is Converging On

The market is converging on:

- persistent project context
- specialized agents or skills
- hooks and lifecycle automation
- MCP or extension ecosystems
- resumable long-running work
- GitHub and workflow-system integration
- background tasking with explicit approvals
- more cross-device continuity

These are no longer differentiators by themselves.

## Where Competitors Are Still Weak

Even the strongest tools still depend heavily on:

- frequent release trains
- manual instruction files
- manual hook authoring
- user-authored setup knowledge
- per-tool product dialects
- fractured continuity between shell, app, and workflow systems

This leaves an opening.

## Jini Wedge

Jini should win as:

- the self-learning work operating system
- the self-correcting orchestration layer
- the cheapest path to a high-quality finished outcome
- the surface that moves quality upstream before users pay in rework

That wedge is stronger than "better coding model shell" because model shells can
copy interaction patterns quickly. They cannot as easily copy:

- durable work identity across surfaces
- policy-driven workflow learning
- automated upstream quality control
- environment-aware repetitive-work elimination
- score-governed self-correction loops

## Self-Learning And Self-Correcting Requirement

Jini should not require weekly user-facing relearns to stay competitive.

The framework should improve through:

- learned environment fingerprints
- learned workflow patterns
- learned route and cost policies
- learned repetitive-task templates
- offline evaluation over stored traces
- shadow testing of new policies before rollout
- automatic contract repair when docs, help, and runtime drift
- automated UX and trust audits against the flagship flows

Code releases should still happen, but the fastest improvement loop should be:

- observe
- evaluate
- learn
- validate
- update policy or behavior contract
- promote only if score and user outcome improve

## Product Research Findings

### Finding 1: Jini should be a work operating system, not a pack launcher

Packs can remain implementation scaffolding, but the product should present one
session graph and one work model to the user.

### Finding 2: Quality must move upstream

Jini should catch likely failure before execution, not only summarize after the
fact. That includes readiness, missing evidence, missing approvals, likely
regressions, and stale assumptions.

### Finding 3: Learning must reduce user work, not add user setup

If a learning system asks the user to write more policy files than the value it
returns, it fails the product mission.

### Finding 4: CLI and apps must be views over the same session graph

The CLI should stay the thinnest, fastest control surface. Desktop and mobile
should expose review, inspection, approval, artifact editing, and continuity.

### Finding 5: Pace should come from policy and evaluation, not constant surface churn

Jini should adopt a slower public UX release cadence than the fastest
competitors while improving continuously through trace-backed policy and
self-correction.

## Research Decision

Jini should pursue one strategic category:

- the self-learning, self-correcting, cross-surface work operating system that
  gets to the desired outcome faster, more cheaply, and with less rework than
  raw model shells or extension-only frameworks.
